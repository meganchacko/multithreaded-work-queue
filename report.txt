Additional Test Configurations
1: ./csmc 15 1 10 5
    This configuration tests 15 students with only 1 tutor and 10 waiting chairs to examine the priority queue functionality and FIFO ordering, to see if the priority queue correctly selects students according to their visit number and preserves the FIFO order for students with the same priority. All 75 tutoring sessions completed succedssfully and there were no unsuccessful chair attempts.

2: ./csmc 50 3 2 5
    This test aims to see how our program handles a relatively large number of students competing for a limited number of waiting chairs, with more than one tutor available and repeat visits to the center. All of the 250 tutoring sessions successfully completed. There were 17 unsuccessful chair attempts due to contention, which demonstrates students arriving to a full waiting room and continuing to retry until they completed their visit.

3: ./csmc 10 30 5 4
    The purpose of this test is to observe our program's behavior when there are significantly more tutors than students, specifically if tutors waiting for requests can exit properly at the end of the program. We saw that all 40 tutoring sessions completed successfully, and there were no unsuccessful chair attempts. The program termination was also successful, so we confirmed that idle tutor threads shut down properly and don't stay stuck waiting for students to arrive.

Synchronization Design:
Our program uses two queues, an arrival and priority queue, along with a shared mutex to maintain them properly. The arrival queue keeps track of the students in the order they sat in the waiting chair, and the priority queue uses the visit number to determine which student receives help next. The number of visits determines a students priority, students with fewer visits are assigned higher priority, and students with the same priority are assisted in a FIFO order. The mutex prevents the multiple threads accessing these queues, and other shared variables, from modifying data simultaneously.

We used semaphores to manage the communication between different threads. Upon a student's arrival, a semaphore alerts the coordinator, and the request gets moved from the arrival queue to the priority queue. We use another semaphore to alert tutors when students become available to assist. The tutor selects the student with highest priority to serve next, which immediately makes their waiting chair available again, and alerts that student's personal semaphore of their assignment.

When all tutoring visits are complete, the program begins shutdown. Any waiting threads are woken and joined together before allocated memory is free and synchronization resources are destroyed.

Bugs and Corrections:
A correction we had to make was making sure that, even when we encounter an error (like a tutor not 
starting), that we aren't immediately jumping to resolve the error by destroying the semaphores. If 
we did this, it would cause a crash since the other tutors would still be waiting within sem_wait. So 
instead, on a tutor or student creation failure we still run the normal shutdown where we set shut_down, 
post coord_sem so the coordinator wakes every tutor, join all threads that were created, and then we destroy 
the semaphores.

A bug we ran into was when a student adds itself to the arrival queue. We originally wrote the new request at arrival_queue[arrival_size], 
which ignores where the head of the queue is. This only works while head is 0. After the coordinator pops 
a request, head moves forward, so the next push lands in the wrong slot and the next pop reads a slot 
that was never filled. With 2 chairs, the coordinator ended up queuing an empty request (student 0), and 
the real student was never woken, so the program would hang. We couldn't tell when there was 1 chair, since 
head always wraps back to 0, so ./csmc 10 1 1 3 passed but ./csmc 2 2 2 2 hung. We fixed it by assigning 
the tail to be (arrival_head + arrival_size) % num_chairs_copy instead.
